# 数据统计接口性能分析与改进报告

> 对应博客 3.3「数据统计接口部分的性能改进」
> 剖析工具：cProfile + pstats（辅以 snakeviz 交互式报告）
> 原始数据：`output/performance/analyze.prof`、`output/performance/benchmark.json`

## 一、剖析方法

统计接口是 `DanmakuAnalyzer.analyze()`：一次遍历完成领域归类、案例匹配、
态度/成本/风险识别、分词与词频统计。用 cProfile 包住整个调用：

```bash
python scripts/profile_analysis.py --sample 3000
```

脚本产出：

| 产物 | 说明 |
| ---- | ---- |
| `output/performance/analyze.prof` | cProfile 原始数据，可 `python -m snakeviz` 打开 |
| `output/performance/profile_report.txt` | 文本版热点函数列表 |
| `output/figures/性能分析_热点函数.png` | 热点函数条形图（累计耗时 vs 自身耗时） |
| `output/figures/性能分析_优化对比.png` | 优化前后对比 |
| `output/html/性能分析报告.html` | 自包含的交互式矩形树图报告（离线可用） |
| `output/performance/benchmark.json` | 基准测试量化结果 |

## 二、热点定位结果

热点函数图见 `output/figures/性能分析_热点函数.png`。
在**全量数据**（61,556 条清洗后弹幕）上的实测结果，总耗时 5.45 秒：

| 排名 | 函数 | 累计耗时 | 占比 | 说明 |
| ---: | ---- | -------: | ---: | ---- |
| 1 | `analyzer.analyze` | 5.448 s | 100% | 统计入口 |
| 2 | `segmenter.segment` | 4.026 s | **73.9%** | **最大瓶颈：jieba 分词** |
| 3 | `jieba.lcut` | 3.073 s | 56.4% | 分词内核 |
| 4 | `matcher.find_labels` | 0.884 s | 16.2% | AC 自动机匹配（5 次/条） |
| 5 | `segmenter._ensure_initialized` | 0.387 s | 7.1% | jieba 词典加载（一次性） |
| 6 | `segmenter.is_meaningful` | 0.236 s | 4.3% | 分词后的 token 过滤 |

### 结论：消耗最大的函数是 `Segmenter.segment`

它内部调用 `jieba.lcut`，占统计接口累计耗时的 **73.9%**。开销来自 jieba 的
DAG 构建 + HMM 新词发现（`__cut_DAG` 2.70 s、`finalseg.cut` 0.97 s）。
弹幕都是短句，无法通过"减少文本长度"来规避，只能通过**缓存复用**降低。

不过多模式匹配只占 16.2%，它确实不是当前的性能瓶颈。
这是"先测量、再优化"的价值所在：如果只凭直觉，很可能会花大量时间继续优化匹配，
而真正的瓶颈（分词）纹丝不动。

## 三、改进措施与量化收益

### 改进一：Aho-Corasick 替换朴素子串匹配

**改进前**（`naive_match_count`）：

```python
for text in danmaku:                       # N 条弹幕
    for name, aliases in lexicon.items():  # M 个类别
        if any(alias in text for alias in aliases):
            counter[name] += 1
```

复杂度 `O(N × M × 文本长度)`。**改进后**：所有别名构建成 Trie + BFS 失败指针，
一次线性扫描同时命中全部模式，复杂度 `O(总文本长度 + 命中数)`。

| 实现 | 单条耗时 | 相对提速 | 全量 61,556 条预估 |
| ---- | -------: | -------: | -----------------: |
| 朴素子串匹配 | 12.2 μs | 1× | 0.75 s |
| Aho-Corasick | 0.98 μs | **约 12.5×** | 0.06 s |

（样本 3000 条弹幕、433 个模式、自动机 1043 个节点，构建耗时 0.5 ms。
耗时取 3 次运行的中位数——只跑一次的话结果抖动很大，同一份代码测出 12 倍和 18 倍都有过）

### 改进二：分词结果缓存（针对剖析发现的最大瓶颈）

弹幕语料存在大量重复表达（"讲得很好""求资料"这类句子会被成百上千个用户发送），
因此给 `Segmenter.segment()` 加了一层按原文缓存的结果字典。

| 场景 | 全量分词耗时 | 缓存命中率 | 相对提速 |
| ---- | -----------: | ---------: | -------: |
| 无缓存 | 1.50 s | — | 1× |
| 带缓存（首次运行） | 1.36 s | 26.8% | 约 1.11× |
| 带缓存（缓存已热） | 0.02 s | 100% | 约 69.9× |

这里分两种情况报告，因为意义完全不同：程序每次运行都是一次"冷缓存"，
所以 **1.11× 才是实际收益**；"缓存已热"的 69.9× 只是理论上限，不能当成优化效果来宣传。

**命中率只有 26.8% 这件事本身也值得说明**：全量数据里 61,556 条弹幕只有
45,038 条唯一文本（唯一率 73%），说明长尾表达非常多——弹幕不是简单的复读，
用户在真实地表达不同内容。因此缓存的收益有限，这也是一个诚实的结论：
**不是所有优化都能带来数量级提升**。

### 改进三（爬虫侧）：三级通道 + 熔断

虽然不属于"统计接口"，但它是本次最大的一处性能改进：

| 方案 | 单视频请求数 | 说明 |
| ---- | -----------: | ---- |
| 单通道 + 指数退避 | 最多 12 次，失败时每次退避约 2 分钟 | 通道级限流下几乎不可用 |
| 三级通道 + 熔断 | **1 次**（主通道命中） | 主通道 `comment.bilibili.com/{cid}.xml` 一次拿全量 |

实测：改之前抓 486 个视频花了 40 多分钟且大量视频是空的，
改之后单视频平均 6 秒左右，空视频基本都是"本身就没有弹幕"。

## 四、设计层面的优化（避免冗余开销，未单独量化）

以下两项是编码时的设计选择，不是剖析后的改动，因此不声称具体收益，
但确实避免了不必要的开销：

1. **jieba 惰性初始化**：`jieba.initialize()` 需要加载词典，实测约 0.39 s
   （剖析中体现为 `marshal.load`）。原实现在模块导入时初始化，任何只用到
   部分功能的调用都要付这份代价；改为首次分词时惰性加载。
2. **一条弹幕只分词一次**：把"整体词频"与"分领域词频"合并到同一次遍历，
   分词结果同时喂给整体计数器与命中领域的计数器，避免了 `O(2N)` 的重复分词。
3. **零弹幕视频短路**：视频元信息里弹幕总数为 0 时直接返回，
   不再发起任何弹幕请求——近期上传的新视频大量属于这种情况，
   原先每个都要白跑最多 12 次分段请求。

## 六、后续可优化方向

| 方向 | 预期收益 | 代价 |
| ---- | -------- | ---- |
| 用 `jieba.lcut` 的 `HMM=False` 关闭新词发现 | 减少约 30% 分词耗时 | 会漏掉未登录词（弹幕里新词很多，不建议） |
| 换用更快的分词器（如 pkuseg / jieba-fast） | 可能有 2~3 倍提升 | 引入新依赖，词典兼容性需验证 |
| 把统计改为多进程 | 接近线性加速 | 弹幕量大时才有必要，当前单进程已足够 |
| 预编译领域词典为 AC 自动机的持久化结构 | 省去每次构建的 0.7 ms | 收益过小，不值得 |
