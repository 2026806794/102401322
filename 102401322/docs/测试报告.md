## 二、测试设计方法

### 2.1 白盒测试（主要方法）

按作业要求以白盒方法为主，针对每个模块的**内部逻辑分支**设计用例：

| 被测对象 | 白盒关注点 | 对应测试 |
| -------- | ---------- | -------- |
| `AhoCorasick` | 失败指针跳转、输出合并这两个优化的正确性 | 与朴素实现在随机语料上**逐项计数等价**的等价性测试 |
| `_progress_bucket` | 分桶边界 | 0%、9.9%、50%、99.9%、越界、时长为 0 |
| `_ranking` | 排序稳定性与并列处理 | 次数相同按名称升序、占比之和为 1 |
| `parse_danmaku_proto` | 手写 varint 解析的各 wire_type 分支 | 构造二进制字节串直接驱动 |
| `_complete_months` / `_contiguous_tail` | 趋势预测的数据质量守卫 | 当月剔除、跨年连续、断点截断 |
| `_need_segment_fallback` | 分段兜底的判定表 | 6 组条件组合的判定表测试 |
| `_request` | 重试、限流冷却、业务错误码分支 | 替身响应对象驱动，覆盖 412 重试与 62002 立即失败 |
| 三级通道降级 | 通道优先级与熔断计数 | 替身客户端注入失败序列 |

### 2.2 等价类划分 + 边界值分析

以弹幕清洗为例，把输入划分为 5 个等价类，并对边界值单独设计用例：

| 等价类 | 代表输入 | 期望 |
| ------ | -------- | ---- |
| 有效弹幕 | "大模型写代码效率很高" | 保留 |
| 词表噪声 | "666"、"前排"、"哈哈哈哈" | 丢弃 |
| 正则噪声 | "12345"、"@张三"、"https://..." | 丢弃 |
| 长度不足 | "好" | 丢弃 |
| 重复刷屏 | 同一用户同视频重复 3 次 | 只保留 1 条 |

边界值用例：单字符重复**恰好 3 次**（保留）与 **4 次**（丢弃）；
token 长度**恰好等于** `min_length` 与**小于** `min_length`。

### 2.3 异常与健壮性测试

| 场景 | 用例 |
| ---- | ---- |
| 缓存文件损坏 | `read_json` 返回默认值；遍历时跳过坏文件 |
| XML 属性字段缺失 | 跳过该条，不中断整批解析 |
| 空输入 | 空弹幕列表、空文本、空媒体文章均返回空结果而不抛异常 |
| 非法时间格式 | `_parse_duration("abc")` → 0；`_normalize_date("不是时间")` 原样返回 |
| 未知 protobuf 字段 | 安全退出解析循环，不崩溃、不死循环 |

### 2.4 回归测试

针对开发过程中发现并修复的真实缺陷，每个都补了回归用例：

| 缺陷 | 回归用例 |
| ---- | -------- |
| 缓存记录缺 `bvid` 导致视频全部归入"未知" | `test_bvid_is_recovered_from_filename` |
| 清洗统计口径不一致（`kept` 未扣除重复） | `test_clean_batch_statistics_are_consistent` |
| `get_logger` 只给首个 logger 挂 handler，INFO 日志丢失 | `test_get_logger_configures_root_logger` |
| 通道返回空数据时误记 `source` | `test_empty_result_does_not_set_source` |

## 三、测试评估：这些用例能满足该程序的测试要求吗？

### 3.1 覆盖充分的部分

* **纯逻辑模块**（清洗、分词、匹配、统计、导出、趋势分析）覆盖率高（92%~99%），
  核心算法（AC 自动机的失败指针、protobuf 解析、趋势守卫）都有针对性用例；
* **数据契约**有测试守住：`AnalysisResult` 可 JSON 序列化、
  `MediaArticle` 可无损往返、大屏注入的 ECharts 配置是合法 JSON 且每个图表都有 `series`；
* **可视化有端到端冒烟测试**：真实调用 matplotlib 出图并校验文件非空，
  能捕获中文字体缺失、数据键名拼错等单测难以发现的问题。

### 3.2 覆盖不足的部分（已知缺口）

| 缺口 | 原因 | 影响评估 |
| ---- | ---- | -------- |
| `bilibili_client` 网络请求路径（52%） | 真实 HTTP 调用需要 mock 或录播，成本高 | 已用替身响应覆盖重试/错误码分支；剩余为 URL 拼装等直白代码 |
| `danmaku_fetcher` 编排路径（50%） | 依赖真实网络与磁盘缓存 | 已覆盖通道降级、熔断、零弹幕短路等关键分支 |
| 真实爬取结果的数据质量 | 单元测试无法验证 | 由 `crawl` 阶段的日志与状态统计（ok/empty/failed 计数）间接验证 |

### 3.3 结论

对**逻辑正确性**而言，现有用例是充分的：所有分支密集的函数都有白盒用例，
所有已发现的缺陷都有回归保护，核心模块覆盖率均在 92% 以上。

对**集成与外部依赖**而言仍有缺口，这是单元测试的固有边界——
网络层的行为通过"替身对象 + 分支覆盖"验证了控制流，而真实接口的字段变化
只能靠运行时日志发现。若要进一步提升，下一步应该补：
用 `responses`/`vcrpy` 录制真实响应做回放测试，以及在 CI 中定时运行爬虫冒烟测试。

### 3.4 自动化程度

测试可一键运行（`python -m pytest`），已配置在 `pytest.ini` 中，
不依赖网络与外部服务，可在任意机器上重复执行——满足作业对"单元测试自动化"的要求。
