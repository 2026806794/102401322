### 分层架构

```
                    main.py (CLI 入口)
                         │
                    pipeline.py (阶段编排)
                         │
   ┌─────────────┬───────┴────────┬──────────────┐
   ▼             ▼                ▼              ▼
crawler  →   processing   →   analysis   →   visualization
 (取数)        (净化)          (统计)          (呈现)
   │             │                │              │
   └─────────────┴────────────────┴──────────────┘
              统一通过「文件契约」通信
    data/raw/*.json → data/processed/*.json(l) → output/*
```

**核心设计原则：阶段之间只通过落盘文件通信，不直接传对象。** 这样任一阶段可以单独重跑
（改统计口径不必重爬），每个阶段也能脱离前后依赖单独测试。后期我调整统计口径时，
只重跑了 `clean → analyze` 两步，几分钟就验证完，这个设计的收益很直接。

## (3.2) 爬虫与数据处理

### 业务逻辑

```
关键词搜索（综合排序 totalrank）
   → 视频清单去重合并（跨关键词按 bvid 去重）
   → 逐视频取 cid
   → 三级通道抓弹幕
   → 原始弹幕落盘缓存（data/raw/danmaku/{bvid}.json）
   → 清洗去噪 + 分词
   → 多标签归类 + 词频统计
   → 导出 Excel / 生成图表
```

### 代码设计（类与函数的关系）

爬虫层有三个类/模块，职责严格分离：

| 模块 | 职责 | 不负责什么 |
| ---- | ---- | ---------- |
| `wbi.py` | 纯函数实现签名算法 | 不发请求 |
| `BilibiliClient` | 会话维持、限流重试、各接口调用、响应解析 | 不管抓哪些视频、存哪里 |
| `DanmakuCrawler` | 任务编排、缓存策略、断点续爬、通道熔断 | 不管 HTTP 细节 |

处理层与 `crawler` 完全解耦：`DanmakuCleaner` 只接受 `{"text": ...}` 这样的字典，
既不认识 HTTP 也不认识 B 站；`Segmenter` 只依赖 jieba 与停用词表。
分析层的 `DanmakuAnalyzer` 只依赖"清洗后的记录列表 + 视频元信息"，
连词典都是通过 `lexicon.py` 注入的。

### 关键函数与算法说明

**① wbi 签名（`wbi.sign_params`）**

B 站自 2023 年起要求 web 接口携带 `w_rid` 签名。算法是：取 `img_key` 与 `sub_key`
拼接成 64 位串，按前端硬编码的置换表重排后取前 32 位作为 `mixin_key`；
请求参数加时间戳 `wts` 后按 key 升序拼接成 query，`md5(query + mixin_key)` 即签名。
密钥每日轮换，失效时自动从 `nav` 接口重新获取。**这一层写成了纯函数并支持注入时间戳，
因此可以写回归测试**——签名算法一旦写错，现象是所有请求都失败，靠日志很难定位。

**② 三级弹幕降级通道（`DanmakuCrawler._fetch_danmaku_by_cid`）**

这是本次爬虫中最有价值的工程改进。实测发现 B 站不同弹幕接口的限流策略不同：

| 优先级 | 通道 | 特点 |
| ----- | ---- | ---- |
| 1 | `comment.bilibili.com/{cid}.xml` | 一次请求拿全量；限流最宽松 |
| 2 | `api.bilibili.com/x/v1/dm/list.so` | XML 结构相同但限流更严，容易持续 412 |
| 3 | `api.bilibili.com/x/v2/dm/web/seg.so` | protobuf 分段（6 分钟/段），属另一限流桶 |

每个通道都带**熔断器**：连续失败 3 次即判定为通道级限流并永久跳过。
为什么必须熔断？因为每次失败都要付出指数退避的时间代价（实测约 2 分钟），
而失败是**通道级**的——同一个通道在这个视频上失败，在下一个视频上同样会失败。
加上熔断后，单视频请求数从最多 12 次降到 1 次，整体耗时下降一个数量级。

`seg.so` 返回的是 protobuf 二进制。我没有引入 protobuf 运行时，而是**手写了 varint 解析器**
（约 50 行）：按 `tag = field_no << 3 | wire_type` 逐字段读取，遇到未知 wire_type 安全退出。
这样少了一个重量级依赖，解析逻辑也完全可测。

**③ 弹幕噪声三层治理（`processing/noise_lexicon.py` + `cleaner.py`）**

| 层级 | 手段 | 例子 |
| ---- | ---- | ---- |
| 整条丢弃 | 精确词表 | `666`、`前排`、`哈哈哈哈`、`求资料`、`已三连` |
| 整条丢弃 | 正则规则 | 纯数字、纯符号、`@某人`、链接、纯 emoji、单字刷屏 |
| 分词过滤 | 停用词 | 虚词 + 灌水词 + 教程类视频的"求资源"高频词 |

另外做了三件事：

1. **文本规范化**：去零宽字符（B 站常见的绕过检测手段）、压缩叠字（"哈哈哈哈"→"哈哈"）、
   剥离内联的 @提及/链接/表情标签；
2. **刷屏去重**：去重键是「视频 + 用户 + 文本」。这里有个判断很重要——
   *同一用户*在同一视频里把同一句话刷多次才算噪声；*不同用户*说同样的话是真实观点共鸣，
   必须保留。我一开始用「视频 + 文本」去重，全量数据下会多删 13469 条
   （比如有个视频里「打开中文字幕」出现了 1476 次，按老口径只剩 1 条），
   那是不同用户在说同一句话，不是噪声；
3. **噪声样本留档**：每类噪声保留 5 条样例写入 `noise_samples.json`，便于写报告时举例。

**④ 多标签领域归类（`analysis/matcher.py`）**

一条弹幕可能同时属于多个领域（"用显卡跑本地大模型写代码"同时命中硬件算力与编程开发），
所以采用多标签计数而非单选分类。433 个别名如果逐个做 `alias in text` 判断，
复杂度是 O(弹幕数 × 别名数 × 文本长度)。我用 **Aho-Corasick 自动机**把它降为
"一次线性扫描"：所有别名构建成一棵 Trie，BFS 补齐失败指针，并把失败链上的输出
合并到当前节点，匹配阶段每读一个字符只需 O(1) 取结果。

**⑤ 进度归一化（`analyzer._progress_bucket`）**

弹幕自带出现时间（秒），但视频时长从 1 分钟到 15 小时不等。统计"弹幕随视频进度的分布"时
必须按各视频时长归一化到 10 个分桶，否则长视频会天然占据绝对优势。

### 异常处理与健壮性

| 场景 | 处理方式 |
| ---- | -------- |
| 单条弹幕 XML 属性字段缺失 | 跳过该条，不中断整批解析 |
| 视频详情缺 cid | 记为该视频抓取失败，写入缓存供下次重试 |
| 接口返回 412 限流 | 指数退避 + 连续 3 次触发 25~45 秒长冷却 |
| 搜索返回空页 | 延迟 8~16 秒重试一次，连续 2 页为空才判定结果结束 |
| 缓存文件损坏 | `read_json` 返回默认值，遍历时跳过该文件 |
| 视频时长缺失 | 进度分桶归入第一桶，不做除零运算 |

## (3.3) 数据统计接口部分的性能改进

### 性能剖析

用 `cProfile` 对统计接口 `DanmakuAnalyzer.analyze()` 做剖析，原始数据保存在
`output/performance/analyze.prof`（可用 `python -m snakeviz` 打开交互式报告），
热点图见 `output/figures/性能分析_热点函数.png`。

剖析结论（全量 61,556 条清洗后弹幕，总耗时 5.45 秒，按累计耗时排序）：

| 函数 | 累计耗时 | 占比 | 说明 |
| ---- | -------: | ---: | ---- |
| `analyzer.analyze` | 5.448 s | 100% | 统计入口 |
| `segmenter.segment` | 4.026 s | **73.9%** | jieba 分词，**最大瓶颈** |
| `jieba.lcut` | 3.073 s | 56.4% | 分词内核（DAG + HMM 新词发现） |
| `matcher.find_labels` | 0.884 s | 16.2% | AC 自动机匹配（每条弹幕扫 5 类词典） |
| `segmenter._ensure_initialized` | 0.387 s | 7.1% | jieba 词典加载（一次性） |

**这个结果和我的直觉相反**：我原以为 433 个模式的多标签匹配会是瓶颈，提前写了 AC 自动机，
剖析后才发现分词才是真正的耗时来源（73.9%），匹配只占 16.2%。

### 改进一：Aho-Corasick 替换朴素子串匹配

虽然剖析显示匹配不是当前瓶颈，但它仍是 O(N×M) → O(N) 的实质性改进，
在数据量放大后收益显著。实测（样本 3000 条弹幕、433 个模式）：

| 实现 | 单条耗时 | 相对提速 | 全量 61,556 条预估 |
| ---- | -------: | -------: | -----------------: |
| 朴素子串匹配 | 12.2 μs | 1× | 0.75 s |
| Aho-Corasick | 0.98 μs | **约 12.5×** | 0.06 s |

（耗时取 3 次运行的中位数。只跑一次的话抖动很大，同一份代码我测出过 12 倍也测出过 18 倍，
所以后来给基准测试加了重复取中位数。）

### 改进二：分词结果缓存（针对剖析发现的最大瓶颈）

既然瓶颈在分词，而弹幕语料存在大量重复表达，就给 `Segmenter.segment()` 加了一层
按原文缓存的结果字典。实测：

| 场景 | 全量分词耗时 | 缓存命中率 | 相对提速 |
| ---- | -----------: | ---------: | -------: |
| 无缓存 | 1.50 s | — | 1× |
| 带缓存（首次运行） | 1.36 s | 26.8% | 约 1.11× |
| 带缓存（缓存已热） | 0.02 s | 100% | 约 69.9× |

这里必须说明一下：程序每次运行都是一次"冷缓存"，所以 **1.11× 才是实际收益**。
"缓存已热"的 69.9× 只是理论上限，我一开始只测了这个数字，看起来特别好看，
但拿它当优化效果就是在骗自己。

**命中率只有 26.8% 这件事本身也是一个发现**：61,556 条弹幕里只有 45,038 条唯一文本
（唯一率 73%），说明弹幕的长尾表达非常多——用户不是在简单复读，而是在真实地表达不同内容。
因此这项优化的收益有限，这也是一个诚实的结论：**不是所有优化都能带来数量级提升**。

优化前后对比图见 `output/figures/性能分析_优化对比.png`，量化数据见
`output/performance/benchmark.json`。

### 消耗最大的函数

**`Segmenter.segment`（内部调用 `jieba.lcut`）是程序中消耗最大的函数**，占统计接口
累计耗时的 **73.9%**。它的开销来自 jieba 的 DAG 构建 + HMM 新词发现（`__cut_DAG` 2.70 s、
`finalseg.cut` 0.97 s）；由于弹幕都是短句，这个开销无法通过减少文本长度来规避，
只能通过缓存复用与词典精简来降低。这也是为什么我把 `jieba` 的初始化改成惰性加载——
在只做部分统计时不必付这份代价。

### 性能改进小结

| 改进项 | 手段 | 实测收益 |
| ----- | ---- | -------: |
| 多标签匹配 | 朴素子串 → AC 自动机 | 12.5×（全量 0.75 s → 0.06 s） |
| 分词 | 结果缓存复用 | 1.11×（命中率 26.8%；缓存全热可达 69.9×） |
| 词典加载 | 惰性初始化 | 按需付出约 0.39 s 的一次性开销 |
| 爬虫 | 三级通道 + 熔断 | 单视频请求数 12 → 1 |
| 爬虫 | 零弹幕视频短路 | 每个空视频省下最多 12 次请求 |

### 可视化大屏的设计思路

大屏用 **CSS Grid + 手写 ECharts 配置**实现，而不是用 pyecharts 的默认模板，原因是：

1. pyecharts 的 `dump_options()` 在饼图与词云上会把数据序列化成
   `{"name": "name", "value": "value"}` 这样的占位符（实测），直接导致图表空白；
2. 默认模板无法自由排版，而大屏需要"指标卡 + 图表网格"的信息层级。

最终结构：

* **顶部指标卡**：有效弹幕总数、覆盖视频数、应用领域类别数、识别案例数、噪声占比——
  先给结论性数字，再让读者看细节；
* **第一行**：词云（左，占半屏）+ 应用领域玫瑰图（右），回答"大家在聊什么"；
* **第二行**：Top8 应用案例 + 用户态度环形图，回答"大家在用谁、态度如何"；
* **第三行**：成本维度 / 风险维度 / 关键词对比，回答"大家担心什么"；
* **第四行**：弹幕进度分布 + 弹幕量 Top10 视频，提供数据质量视角。

配色统一为深蓝科技风（`#0F1B2D` 底 + `#4C8DFF`/`#38D9C0`/`#FFB84C` 强调色），
所有图表透明背景以融入渐变底色；ECharts 静态资源放在 `output/assets/` 本地引用，
**断网也能正常打开**。

> 补充说明：词云以静态高清图嵌入大屏，而不是用 `echarts-wordcloud` 插件。
> 原因是该插件是针对 ECharts 4 编译的（内部调用已废弃的 `extendSeriesModel`），
> 在 ECharts 5 下无法注册系列类型，图表会静默空白。与其降级图表引擎，
> 不如直接复用本项目自己生成的中文词云图，既避开兼容性风险，观感也更好。

# 三、心得体会

## 1. 反爬对抗比爬虫本身更花时间

这次最大的认知更新是：**写爬虫的时间主要不是花在"发请求 + 解析"上，而是花在"如何稳定地
持续拿到数据"上**。B 站启用了 wbi 签名、对弹幕接口做了分级限流，我最初的实现每遇到 412
就退避重试，结果大量视频被标记为"空"。后来通过实测发现不同接口的限流策略不同，
才设计出三级降级通道 + 熔断机制。这个过程让我理解了"熔断"这个在微服务里常见的模式，
在爬虫里同样是刚需——**当失败是通道级的时候，重试是纯粹的浪费**。

## 2. 性能优化必须先测量，不能凭直觉

我原本以为 433 个模式的多标签匹配是性能瓶颈，提前写了 Aho-Corasick 自动机。
用 cProfile 剖析之后才发现，**分词占了 74% 的累计耗时，而匹配只有 16%**。
于是我针对真正的瓶颈补了分词缓存，命中率 26.8%——收益有限，
但也让我意识到"弹幕并不都是复读"：61,556 条里唯一文本占 73%，用户在真实地表达不同内容。
如果只凭直觉优化，很可能是"优化了不重要的地方，还自我感觉良好"。

## 3. 统计口径的每一个选择都要能自圆其说

做文本统计时会遇到大量"看起来无所谓"的选择，但每一个都会影响结论：

* **去重粒度**：一开始按「视频 + 文本」去重，实测会多删 13469 条不同用户的相同观点。
  举个具体的例子：有个视频里「打开中文字幕」这句话出现了 1476 次，按老口径只剩 1 条，
  但那其实是 1476 个不同用户在表达同一个意思。
  改为「视频 + 用户 + 文本」后，只有同一用户刷屏才算噪声——**"很多人说同一句话"本身就是信号**；
* **多标签 vs 单标签**：一条弹幕可能同时属于多个领域，强行单选会丢信息，
  所以采用多标签计数，并在报告中说明"各类之和大于总数"；
* **进度归一化**：不按视频时长归一化的话，15 小时的课程视频会碾压 1 分钟的视频。

这些判断没有标准答案，但必须**在报告里写清楚口径**，否则读者无法判断结论是否可信。

## 4. 先定义数据契约，再写实现

项目里各阶段之间用 JSON/JSONL 文件通信，而不是直接传 Python 对象。
这个选择在后期反复调整统计口径时收益巨大——改一次规则只需重跑 `clean → analyze`，
几分钟就能验证，不必重新爬数据。同时每个阶段都能脱离前后依赖单独写单元测试，
155 个测试用例里有相当一部分是这么来的。

## 5. 代码复审确实能发现真问题

复审阶段发现并修复了 3 个真实缺陷，都不是靠"看代码风格"发现的，而是靠追问
"这个分支真的会被走到吗"：

1. 短视频的 XML 通道失败后不会触发 protobuf 兜底（条件写成了 `segments_needed > 1`）；
2. 搜索接口被限流返回空页时被误判为"结果结束"，导致某个关键词只抓到 36 个视频就停了；
3. `get_logger` 只给第一个创建的 logger 挂了 handler，导致其他模块的 INFO 日志被静默丢弃，
   排查限流问题时因为"日志里什么都没有"而误判为"程序卡住了"。

这三个问题我都补了回归测试。**尤其是第三个——日志不工作比功能不工作更难排查，
因为它让你失去了排查手段本身。**

## 6. 静态检查工具确实能查出东西

以前觉得 flake8、pylint 这种工具就是挑格式毛病，这次认真跑了一遍才发现不是。
flake8 报的 36 个警告里确实大部分是格式问题，但 pylint 查出的两个是实打实的错误：
噪声词表里同一个词写了两遍（不报错，但说明我当时复制粘贴没检查），
`Timer` 的 `start` 属性定义在 `__enter__` 里（能用，但不符合规范，别人看代码会困惑）。

改完最大的感受是：**"能跑"和"写对了"是两回事**。单元测试保证的是"跑起来结果对"，
静态检查保证的是"代码本身没毛病"，两个都得有。

## 7. 对"大模型应用"这个题目本身的感受

做完数据之后回头看，最触动我的不是技术，而是数据本身呈现出的**温差**：
B 站用户在热烈讨论"用大模型学什么、怎么学"，教育类话题占了弹幕话题的近三分之一；
而科技媒体的报道重心则在办公效率、编程开发和科研学术。用户关心"我怎么学会它"，
媒体关心"它会改变哪个行业"。

同时，用户对成本（API 费用、显卡价格）和风险的讨论也相当具体——不是抽象的"AI 会不会毁灭人类"，
而是"这个月 API 又花了多少钱""显卡太贵了本地部署跑不动""AI 写的东西不敢直接用，怕有幻觉"。
这种务实的关切，可能比任何宏大叙事都更接近大模型技术落地的真实状态。
