## 一、预估与实际差异说明

| 环节 | 偏差 | 原因分析 |
| ---- | ---- | ---- |
| Analysis（+15） | 偏多 | B 站自 2023 年起对 web 接口启用了 `wbi` 签名，需要额外学习置换表算法与密钥刷新机制。 |
| Coding（+50） | 偏多 | 原以为用第三方 SDK 即可，实测其维护滞后；改为自行实现签名与弹幕双通道（XML + protobuf），并处理 412 限流。 |
| Code Review（+10） | 偏多 | 复审时发现两个真实缺陷：① 短视频 XML 失败后不会走 protobuf 兜底；② 搜索接口被限流返回空页时被误判为"结果结束"而提前终止。两者都补充了回归测试。 |
| Test（+0） | 持平 | 采用等价类划分 + 边界值分析设计用例，并针对 Aho-Corasick 的失败指针做了等价性测试，用例一次通过率较高。 |
| 合计（+110） | 偏多 12.5% | 主要来自"反爬对抗"这一在预估阶段被低估的环节。 |

## 三、过程改进计划（Postmortem）

1. **反爬环节要单独预留时间**。本次预估时把爬虫当成"发请求 + 解析"，
   实际上签名、限流退避、断点续爬、双通道兜底占掉了爬虫模块近一半工作量。
   下次遇到同类任务，应在 Analysis 阶段先做一次"接口可用性探测"再估时。
2. **先定义数据契约，再写实现**。本项目各阶段之间用 JSON/JSONL 文件通信，
   因此清洗、统计、可视化可以各自独立重跑与测试，返工成本很低——这一点在
   后期调整统计口径时收益明显，值得固化到以后的习惯里。
3. **性能优化要先测再改**。最初凭直觉认为"多模式匹配"是瓶颈并写了 AC 自动机，
   但剖析后发现分词才是 80% 的耗时来源，于是又补了分词缓存。
   先剖析、再优化，避免把时间花在非瓶颈上。
