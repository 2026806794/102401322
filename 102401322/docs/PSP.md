## 一、预估与实际差异说明

| 环节 | 预估 → 实际 | 原因分析 |
| ---- | ---------- | -------- |
| Analysis | 60 → 130（+117%） | 估的时候以为查查文档就行，实际 B 站要 `wbi` 签名（照着前端 js 的置换表算法自己实现），protobuf 的 varint 编码也是现学的。 |
| Coding | 330 → 520（+58%） | 最大的一块超支。原以为爬虫就是"发请求 + 解析"，实际上反爬对抗占了一大半：一开始只用 `list.so` 一个接口，被限流后大量视频抓不到，反复试错才做出三级通道 + 熔断。 |
| Code Review | 45 → 75（+67%） | 复审时发现 3 个真实缺陷（见博客 3.2），每个都要改代码 + 补回归测试。 |
| Test | 120 → 155（+29%） | 用例本身写得快，但有几条一开始把期望值写错了（比如想当然地假设中文按拼音排序，实际是按 Unicode 码点），调试花了时间。 |
| Design / Postmortem | 60 → 50、90 → 70 | 这两项反而提前完成了——分层设计清楚之后不用抠太细；总结写得也比较顺。 |
| **合计** | **880 → 1165（+32.4%）** | 第一次做这类任务，估时普遍偏乐观。最该吸取的教训是：动手前先做一次接口可用性探测再估时。 |

## 三、过程改进计划（Postmortem）

1. **反爬环节要单独预留时间**。本次预估时把爬虫当成"发请求 + 解析"，
   实际上签名、限流退避、断点续爬、三级通道兜底占掉了爬虫模块近一半工作量。
   下次遇到同类任务，应在 Analysis 阶段先做一次"接口可用性探测"再估时。
2. **先定义数据契约，再写实现**。本项目各阶段之间用 JSON/JSONL 文件通信，
   因此清洗、统计、可视化可以各自独立重跑与测试，返工成本很低——这一点在
   后期调整统计口径时收益明显，值得固化到以后的习惯里。
3. **性能优化要先测再改**。最初凭直觉认为"多模式匹配"是瓶颈并写了 AC 自动机，
   但剖析后发现分词才是 74% 的耗时来源，于是又补了分词缓存。
   先剖析、再优化，避免把时间花在非瓶颈上。
